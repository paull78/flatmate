## Tooling notes

- `scripts/` is the `@fm/scripts` workspace package (a CLI shell with Node typings); it may import `@fm/domain` and `@fm/protocol` only, through their entries (depcruise rule `scripts-import-domain-and-protocol-only`; `depcruise packages scripts`) (2026-09-29, phase 8 Task 8.1).
- Seed data goes through `decideSubmit` (same seq, versions and receipts as live edits); seed scripts live in `packages/server/scripts/`, outside `src/`, because they import `@fm/domain`. `pnpm demo:seed` is idempotent; a crash between create and save leaves an empty "Sample apartment" that the next run returns unfilled (accepted) (2026-09-29, Task 8.4).
- Editor tests run without DOM or Node types, so `console` is undeclared: a test that prints (the narrated demo's `console.table`) declares the one member it uses (2026-09-29, Task 8.3).

- Sync tests (2026-09-29, phase 7 Task 7.11): `@fm/sync-tests` drives two `FakeShell` editors against the real server app with a pump/idle/deliver loop; `@fm/editor` exports its harness as `@fm/editor/testing`; `@fm/server` exports its app from `src/index.ts`; `FakeHost` takes an ID prefix per editor. Real server rules in every sync scenario, with full control of message order.

- Web mode (2026-09-29, phase 7 Task 7.15): `?server=` wins over `VITE_SERVER_URL`, `?server=off` forces local mode; the WebSocket adapter is created in `mountCanvas` before the effect runner is set, so no server event is lost before effects can run. One build serves both modes; the phase 4 smoke test stays local.

- Durability (gate 6, 2026-09-29): an `ack` means the OS reported the tmp write, `FileHandle.sync()`, rename and directory sync complete (Node 22.14). Whether libuv's fsync on macOS forces the drive cache (`F_FULLFSYNC`) was not verified; claim only "saved before acknowledged", never power-loss durability.

- WebSocket transport (2026-09-29, phase 6 Task 6.10): `startWsTransport` is async (the port is known only after `listening`, which tests need for `port: 0`); `ws` `maxPayload` is 16 × `MAX_MESSAGE_BYTES`, so 1–16 MB messages get `tooLarge` from the app and larger frames close the socket.

- JSON repository (2026-09-29, phase 6 Task 6.8): one `<DATA_DIR>/<id>.json` per project holding the whole `ProjectState`; saves go tmp → `FileHandle.sync()` → rename → directory sync where supported; `*.tmp` files are ignored on load; only IDs matching `^[A-Za-z0-9_-]{1,128}$` are loaded, because wire IDs allow `/` and `.`. No power-loss durability claim (whether macOS `fsync` flushes the drive cache was not verified).

- TypeScript is pinned to `~6.0`: `typescript@latest` is 7.x (native port), and typescript-eslint 8.70 accepts only `<6.1.0` (2026-09-27, found while writing phase 1).
- Versions resolved at planning time: vitest 5.0.2, eslint 10.11.0, typescript-eslint 8.70.1, dependency-cruiser 18.4.0, tsx 4.23.15; Vite 8.3.1 arrives as Vitest's peer, so `@fm/web` uses Vite 8 (2026-09-27).
- Gate 1 confirmed the same versions in the real workspace (typescript 6.0.3, esbuild 0.28.2 postinstall allowed, no peer warnings); typescript-eslint's peer range is still `<6.1.0`, so the pin stays (2026-09-27).
- Run one test file with `pnpm --filter <pkg> test <pattern>`; `test -- <pattern>` passes a literal `--` and Vitest runs everything (2026-09-27).
- `.cjs` config files (dependency-cruiser) need a CommonJS globals block in `eslint.config.js` (2026-09-27).
- Under pnpm's strict layout, a bare `@fm/<pkg>` import that is not a declared dependency fails dependency-cruiser as `no-unresolvable`, not as a ring rule; ring rules fire only on resolvable imports (2026-09-27).
- The planning scratch runs of phases 2+ linted only typescript-eslint's assertion rule, not the full `eslint.config.js` (`@eslint/js` recommended included). Expect core `no-*` rule findings in plan code; the first was `no-useless-escape` on `\/` inside the ID regex character class (2026-09-27, Task 2.3).
- Ring rules check direction only. A relative import into another package's internals passed tsc, lint and depcruise until the `only-through-package-index` rule (found 2026-09-28 by the user's question "do packages use each other's files freely?"; probe run in Task 2.4).
- JS objects list integer-like keys ("12") first in numeric order, whatever the insertion order, so `serialize`'s sorted tables are sorted only for non-integer-like IDs. Receipt fingerprints use `canonicalJson`, which sorts keys itself; don't claim canonical file output (2026-09-28, Task 2.17).
- Agent worktrees live in `.claude/worktrees/` inside the repo; `.gitignore` and the ESLint ignores exclude it so `eslint .` in the main tree does not lint agent copies (2026-09-28).
- Vitest 5 hides `console.log` output of passing tests; use `--silent=false` for timing logs (2026-09-27). When an agent runs the tests Vitest picks a quieter reporter and even that may not show them; `--reporter=verbose` does (2026-09-28, wave 5 code review).
- Compare float results with a tolerance (`toBeCloseTo`, `expect.closeTo`), not after `toFixed`: the demo's 9.936 m² sits 0.001 m² from a rounding boundary (2026-09-28, wave 5 code review).
- `applyPatch` rebuilds tables, so after an inverse patch the key order differs from the original document: `toEqual`/`deepEqual` match, `JSON.stringify` does not. Compare documents structurally, never by `JSON.stringify` (except to check that one object was not mutated) (2026-09-28, wave 3 review).
- Planning-time measurement (scratch run of the phase 2 code): a 312-wall document validates in about 14 ms and derives zones in about 8 ms (2026-09-27). Re-measured in Task 2.19 (first call in the test worker, 3 runs): 13.4–14.2 ms and 6.7–7.0 ms. Warm medians after the wave 5 review (20 runs): `validateDocument` ≈6 ms, `zones` ≈2.5 ms, `execute(moveJoints)` ≈6 ms, so a drag preview costs about one validation. Don't quote any of these as a performance claim.
- Domain tests compile with the core `lib: ES2022, types: []`, so `console` and `performance` are unknown to `tsc` there. A test that needs them declares them locally (`declare const performance: { now(): number }`); don't add DOM or Node types to a core package's test config (2026-09-28, Task 2.19).
- Vitest strips type-only imports, so a test file that imports only types passes `vitest` before its sources exist; its red step is `pnpm --filter <pkg> typecheck` (2026-09-28, Task 3.3).
- Core packages have no `@types/node`; once phase 6 adds it for the server, repeat the check that `process` in a core source fails typecheck (2026-09-27).
