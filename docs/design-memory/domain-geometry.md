## Decisions

| Decision | Why | Spec |
|----------|-----|------|
| Initial document = joints, walls, zoneLabels. **Store source data only**; outlines, zones, areas and wall helper lengths are derived (2026-09-27) | Standalone dimension records are a later feature; clients derive identical geometry | §3.2, §11 |
| Invariants I1–I8 in `validateDocument`, used by `execute`, client pre-check and server validator | One definition of "valid" everywhere | §3.3 |
| Planar wall graph: `addWall` splits when an endpoint lands on a wall; interior crossings and collinear overlap are rejected (2026-09-27) | T-junctions suffice for the demo and avoid multi-split normalization | §3.3–3.4 |
| **Min edge 0.01 m**, thickness supplied by domain constant `WALL_THICKNESS = 0.20`; no per-wall field (2026-09-26) | Replaced rev-3's 0.50 m min length, which forbade realistic dividers (e.g. 0.30 m from a corner) | §3.2–3.3 |
| **Topology rule**: only `addWall`/`deleteEntities` change topology; moves/resizes whose *result* is invalid → `DomainError topology` | Moves would otherwise need new IDs and normalisation | §3.4 |
| **Destination only, not path**: a move is a teleport; no swept-path check anywhere | Simplest; a drawing, not a physics sim | §3.4 |
| Deterministic normalisation: caller `opId`, IDs `${opId}/j0…`, lexicographic entity order, endpoint ties by ID; split keeps ID on the `a`-side fragment | Replays and all clients give identical IDs | §3.4 |
| Query results are deeply read-only: `Face`, `Zone`, `zones()` and `orphanLabelIds()` use `readonly` fields and arrays, rings and floors are `readonly Readonly<Point>[]`, ring helpers accept `readonly Point[]`, and the scene's polygon `points` is `readonly Point[]`; documents are treated as immutable values because the memo is keyed by identity (2026-09-28, wave 1 and 2 code reviews) | One memoized analysis per document is shared by every caller; an in-place sort (the planned 2.13 test did one) or a point write would corrupt it for all | §3.6 |
| A command whose result equals its input within tolerance returns an empty patch: `setWallLength` to the current length (within 1e-9) does not recompute the moving joint (2026-09-28, wave 2 code review). A no-op also returns the input document itself; `execute` enforces this for every command (2026-09-28, wave 4 code review; before that each command did it and `moveJoints` was missed) | The float round trip changed the last digit 22–29% of the time, producing noise commits that stamp versions (collaborator conflicts), clear redo and add do-nothing undo steps. Keeping identity keeps the zones memo, which is keyed by document identity | §3.4, §4.1 |
| `execute` promises a valid result only for a valid input: geometry commands run `validateDocument`; label commands shape-check only the label they write (labels take part only in I8); no-ops return the input unchanged (2026-09-28, wave 4 spec review) | Every document reaching `execute` came from `execute`, `deserialize` or the server, which all validate; re-validating on a rename adds nothing. The old comment and spec sentence claimed more | §3.3, §3.4 |
| Label resolution picks the innermost face containing the point among all faces, then refuses it when it is not simple or the point is on its boundary (2026-09-28, wave 2 code review) | Skipping non-simple faces first let a label inside an unsupported inner room resolve to the outer room | §3.6 |
| Zones: remove bridges → components → face walk (y up) → drop each component's exterior → ignore < 0.01 m² → merge collinear → inset 0.10 m with direction check → else "Area unavailable" | Conservative; never invalidates the drawing | §3.6 |
| Initial area display covers simple rooms and a two-room divider; unsupported complex faces may show unavailable area (2026-09-27) | Avoid elaborate topology semantics outside the demo | §3.6, §11 |
| Labels are stored annotations; deleting a divider between two labelled rooms combines names with ` / ` in label-ID order, in the deletion patch (2026-09-26; narrowed 2026-09-27). The rule counts labels, not rooms: exactly two surviving labels in one supported face that resolved to different faces before; three rooms in a row with only the outer two labelled give `One / Three`; three or more labels stay unchanged (2026-09-28, wave 3 spec review) | One label retains both names; undo restores separate labels and geometry together. Counting labels is the rule the code implements and is simpler than tracking which former rooms merged; an unlabelled room contributes no name anyway | §3.4, §3.6 |
| A combined name is cut to 200 UTF-16 code units without splitting a surrogate pair; label names may be empty (2026-09-28, wave 3 spec review) | `.slice(0, 200)` left a lone high surrogate (a broken glyph) that `isValidName` accepted. An empty name contributes nothing to a merged name (`""` + `Dining` → `Dining`, not ` / Dining`; 2026-09-28, wave 3 code review). Empty names: the spec was silent, the properties panel sends on blur, and a nameless label still shows its area; refusing would add a message and a toast for no demo value. Accepted: a cut can leave a trailing ` / `, and grapheme clusters (ZWJ emoji, flags, combining marks) can still be split; only code points are kept whole | §3.3 I8, §3.6 |
| Delete dependencies are the selected entities, walls deleted with a selected joint, and the endpoints of deleted walls; walls that merely keep an endpoint alive are not dependencies (2026-09-28, wave 3 spec review). A label merge adds both source faces' boundaries **and the merged face's boundary**; cleanup removes only endpoints of deleted walls, so every deleted joint is a dependency (2026-09-28, wave 3 code review) | Two users deleting the two walls at a corner write disjoint entities; the second is rejected as `invalid` (I3), the ordinary "invalid together" outcome of §4.0, and both clients converge. Adding neighbour walls would only change the rejection reason to `conflict` | §4.0, §4.1 |
| `execute` returns `DomainPatch` (puts, deletes, `before` values, semantic `dependencies`); no versions in the domain | Collaboration metadata belongs to the editor | §4 |
| `addWall` IDs: new wall always `${opId}/w0`; split fragments `w1`, `w2`; new joints `j0`, `j1`; each in `from`-then-`to` order (2026-09-27) | The old "j0, w0, … in that order" was ambiguous; tests need predictable IDs | §3.4 |
| Degree-1 wall ends are flat at the joint (2026-09-27) | "Square cap" could mean extending past the joint; CAD walls end flush | §3.5 |
| Outlines: at joints with 3+ walls each outline passes through the joint point (covers T/Y/X centres); inner corner reaches are rescaled to meet when they sum to more than L − 2·EPS, and repeated points are dropped. Every outline is a CCW polygon within its body plus outer miters/bevels; checked on 1071 L/U and 2141 T/H/X/fan configurations (2026-09-28; the user asked to favour correctness) | Wave 1 outlines left a 20 cm notch at each end of the demo divider, self-intersected for a 0.05 m wall between inside corners, and spiked 1.29 m past 1 m walls at 5° | §3.5 |
| Risk (2026-09-29, wave 7 code review): every preview and drag move runs a full `execute`, whose whole-document validation grows faster than linearly: about 3.5 ms at 220 walls and 17 ms at 480 (one pointer move with the scene ≈ 5 ms and 19 ms). Fine for the demo (tens of walls); past a few hundred walls a move misses a 60 Hz frame. A fix belongs in the domain (check only around the moved joints), not in the editor; Gate 3's scene-cost question revisits it | Measured on an n × n grid of 1 m rooms | §3.3, §5.7 |
| Accepted limitation: walls shorter than about 2× thickness can leave small slivers of body unfilled near a joint, because a clamped corner is not shared with the neighbour (e.g. a T with a 0.05 m stem leaves ≈0.0075 m²) (2026-09-28) | Closing it needs neighbours to agree on shared clamped corners (or rendering bodies plus joint caps); demo walls are unaffected | §3.5 |
| IDs never name an `Object.prototype` member (`constructor`, `__proto__`, `toString`, …): `isValidId` refuses them, and `execute` checks every ID a command names first, with one message ("Invalid ID"); each command also checks its own lookups. The wave 4 code review suggested dropping the `execute` guard as duplicate; kept, because it covers any future command by construction (2026-09-28, wave 1 spec review; wave 4) | Tables are plain objects: `doc.joints["constructor"]` finds an inherited member (a crafted file or changeset passed I1 with a wall to a missing joint), and a `__proto__` key vanished on load | §3.3 I8 |
| Planning-time rules for phase 2 (2026-09-27): a command that changes nothing returns `ok` with an empty patch and the editor skips the commit; equal-distance endpoint ties use a 1e-9 tolerance, smaller ID wins; `labelZone` refuses a labelled face; a merged name is cut to `MAX_NAME_LENGTH`; faces whose walk repeats a joint get no area and hold no labels; a reused `opId` prefix is refused | Simplest readings of gaps found while writing and running the phase 2 code | §3.4, §3.6 |
| Serialization: min-version on save, JSON-visitor migrations on load, newer versions rejected, unknown fields **not** preserved: unknown top-level fields are dropped, unknown entity fields are rejected (2026-09-29, phase 6 review: the same `parse*` guard the server relies on) | Common file-format pattern; preservation conflicts with a closed model; one strict entity parser for files and the wire | §3.7 |
| Test every invariant I1–I8, including malformed fields and non-finite values; initial I8 has no dimension anchors (2026-09-27) | Shape validity must be covered alongside geometry validity | §3.3, §9 |
| Labels follow their room on moves: `moveJoints`/`setWallLength` relocate a label whose point left its face (same face key = sorted boundary wall IDs) to the floor centroid, else the widest scanline span's midpoint; untouched labels keep their object; relocated labels and their room's boundary go into the dependencies (2026-09-29, user bug report) | A dragged divider passed a label: its room lost its label (no fill) and the neighbour showed two tags. Accepted (review): two concurrent in-flight moves of one room can still orphan its label (both clients converge); locking the room on every move would make ordinary concurrent edits conflict | §3.6, §4.1 |

## Don't

- Don't leave a label where a move pushed it: rooms are derived from its point, so a moved wall can silently reassign it to the neighbouring room (2026-09-29).

- Don't add dimension entities or anchor fallback logic to the initial schema, or normalize interior crossings in initial `addWall` (2026-09-27, §3.2–3.4).
- Don't require nested/bridge-connected area semantics or merges of three or more labels for the initial demo (2026-09-27; "three-room" corrected to "three-label" 2026-09-28, §3.6).

- Don't preserve separate labels after merging labelled rooms; that earlier choice is superseded by slash-joined names. Don't split names by parsing slashes (2026-09-26).

- Don't store fixed thickness on each wall. That superseded representation duplicated a constant and introduced invalid states; future variable thickness needs a schema migration (2026-09-26, §3.2).

- Don't stop invariant test coverage at I7; I8 covers entity shape and finite numeric values (2026-09-26).

- Don't assume one outer face per graph — there is one per connected component (critique 1).
- Don't trust "self-intersection or non-positive area" to detect collapsed insets: a 0.10 m square with 0.20 m walls insets to a flipped **positive-area** square. Use the edge-direction check (critique 2).
- Don't subtract dangling/bridge walls from room area.
- Don't mutate arrays or points returned by domain queries (copy before sorting), and don't mutate a document after querying it (2026-09-28).
- Don't recompute a coordinate that a command leaves unchanged; float round trips create noise patches (2026-09-28).
- Don't index a document table with a string that has not passed `isValidId`, and don't build composite keys with a separator from the ID alphabet (`:` is legal in IDs; use `|`) (2026-09-28, wave 1 review). What counts as checked (2026-09-29, phase 3 wave 4 review): an ID that came from a validated document's own keys (`sortedIds`, hit-tests, a validated wall's `a`/`b`, a selection kept by `pruneSelection`, a tool target taken from those) cannot name an `Object.prototype` member, because `validateDocument` rejects such keys (I8). Strings from outside (wire messages, UI input, test fixtures, exported helpers that take any string) must pass `isValidId` or `entityExists` first.
- Don't leave inner miter corners unclamped (superseded 2026-09-28): accepting self-intersecting or spiking outlines as a "stated constraint" drew area that is not wall.
- Don't route an outline straight across a joint with 3+ walls (it left the T/Y/X centre unfilled: the demo divider showed a notch); don't pin a notched shape as the expected T outline (2026-09-28).
- Don't assume the union of outlines covers every wall body exactly for walls under ~2× thickness (see the limitation), and don't assume every edge is at least 1 mm (2026-09-28).
- Don't cut user text at a fixed code-unit index without checking for a split surrogate pair (2026-09-28, wave 3).
- Don't limit a merge's dependencies to the source faces: with an unlabelled room between the labelled ones, a concurrent deletion of the middle room's wall opened the room and the merge was still accepted. Depend on the merged face's boundary too (2026-09-28, wave 3 code review).
- Don't apply a per-command rule (ID guard, no-op identity) to some commands only: put it in `execute`, where every command passes, and pin it with one test that loops over the commands. `moveJoints` kept returning a copy for a no-op after the other commands were fixed (2026-09-28, wave 4 reviews).
- Don't write round-trip tests that a do-nothing command passes: `apply(doc, invert(empty))` equals `doc`; assert the patch writes something (2026-09-28, wave 4 code review).
- Don't promise cross-platform bitwise numerical identity.
- Don't reintroduce the 0.50 m minimum wall length.
- Don't sell memoization-by-identity as a performance strategy; it only avoids recomputation within one state.
